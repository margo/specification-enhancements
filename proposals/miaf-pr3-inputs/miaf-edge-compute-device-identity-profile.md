# Edge Compute Device Identity Profile (PR3 input)

> **Status.** This document captures the **Edge Compute Device Identity Profile** specified by the MIAF v0 draft, before PR2 deferred the device-identity profile decision. It is preserved as candidate input for whichever release picks up the device identity profile work — likely PR3, but possibly later if the profile lands alongside DFM work post-GA.
>
> The framing decision — is device identity a **foundation** for WFM Client identity (the framing this profile assumes) or a **peer profile** (one of several bootstrap mechanisms for WFM Client SVID issuance, alongside operator-pre-provisioning, enrollment-token, FDO, etc.) — is open. The v0 draft assumed the foundation framing; readers should evaluate the design with that in mind.
>
> See [`../margo-identity-and-authorization-framework.md`](../margo-identity-and-authorization-framework.md) for the active PR2 spec and [`README.md`](README.md) for context.

## Overview

This profile applies MIAF to **Edge Compute Devices**, specifying the SPIFFE ID structure, X.509-SVID constraints, lifecycle, and key-protection requirements for a device's **Logical Device Identity (LDI)** within a Trust Domain.

Related PR3-input documents:

- [`miaf-factory-certificate-bootstrap-method.md`](miaf-factory-certificate-bootstrap-method.md) — the only bootstrap method this profile permitted in v0.
- [`miaf-margo-json-enrollment-protocol.md`](miaf-margo-json-enrollment-protocol.md) — the enrollment surface used to issue device SVIDs.
- [`miaf-device-replacement.md`](miaf-device-replacement.md) — proposed rebinding semantics for hardware replacement.

## 1. Profile scope

This profile applies to all Edge Compute Devices in a Margo deployment.

## 2. Logical Device Identity

A device's LDI is identified by a SPIFFE URI and represented by an X.509-SVID called the **Device SVID**:

```text
spiffe://<trust-domain>/margo/device/<uuid-v4>
```

The `<uuid-v4>` component:

- **MUST** be a random RFC 4122 version 4 UUID generated by the MIS;
- **MUST** use lowercase hex with hyphens;
- **MUST NOT** be predictable or sequential; and
- **MUST** remain unchanged across the LDI's lifetime, including SVID renewal and operator-permitted key rotation.

The LDI is designed to remain stable across hardware replacement or firmware updates; the policy-controlled rebinding semantics that realize this are sketched in [`miaf-device-replacement.md`](miaf-device-replacement.md).

## 3. Logical Device Identity lifecycle

The LDI follows the lifecycle vocabulary defined in the active MIAF [Lifecycle Vocabulary](../margo-identity-and-authorization-framework.md#lifecycle-vocabulary). Device-specific behavior:

| Lifecycle Phase | Description |
| :---- | :---------- |
| **Enrollment** | The device (or its operator) presents a **Bootstrap Credential**. The MIS validates it according to the selected method and issues an initial X.509-SVID representing a new (or matched) LDI. |
| **Active** | The device uses its valid SVID to authenticate to Margo components within the Trust Domain. |
| **Renewal** | Before expiry, the device renews its SVID via an authenticated request (e.g., mTLS with the current SVID). Renewal semantics, including rate-limiting and backoff, are defined in [`miaf-margo-json-enrollment-protocol.md#4-svid-renewal-endpoint`](miaf-margo-json-enrollment-protocol.md#4-svid-renewal-endpoint). |
| **Revocation / Termination** | The MIS invalidates the LDI when keys are compromised, the device is decommissioned, or policy mandates retirement. Once revoked/terminated, an LDI **MUST NOT** be re-issued. |

## 4. Profile-specific constraints on the X.509-SVID profile

This profile refines the MIAF [X.509 SVID Profile](../margo-identity-and-authorization-framework.md#x509-svid-profile) for device identities. The MIS **MUST** issue device SVIDs as follows:

| Field | Requirement | Notes |
| :---- | :---------- | :---- |
| **Subject Alternative Name (URI)** | Exactly one URI SAN containing `spiffe://<trust-domain>/margo/device/<uuid-v4>`. | The Margo device path convention. The SAN is the authoritative device identity. |
| **Validity** | **MUST NOT** exceed **5 years**. **RECOMMENDED:** ≤ **90 days** for regularly online devices. | SPIFFE does not constrain validity. Shorter lifetimes reduce risk; operators may choose longer for intermittently connected fleets. |

All other fields **MUST** comply with the base MIAF X.509-SVID profile.

## 5. Profile-specific enrollment and identity issuance

Device enrollment uses the Margo-JSON enrollment endpoint in [`miaf-margo-json-enrollment-protocol.md`](miaf-margo-json-enrollment-protocol.md) with the following constraints:

- The only permitted `svidProfileUri` for devices is `https://margo.org/profiles/spiffe/x509-svid/v1`; other values **MUST** be rejected with `422` (`unsupported-svid-profile`).
- Device enrollment **MUST** use the [Factory Certificate Method (mTLS)](miaf-factory-certificate-bootstrap-method.md); future SUPs may register additional methods. Both the device and the MIS **MUST** implement this method for baseline interoperability.
- The device-profile constraints in this section (X.509-only `svidProfileUri`, Device Key Protection, the LDI lifecycle) **MUST** be honored.

## 6. Device key protection

All device-identity cryptographic operations (key generation, CSR signing, SVID issuance) **MUST** comply with the MIAF [Cryptographic Requirements](../margo-identity-and-authorization-framework.md#cryptographic-requirements). Device private keys **MUST** be protected as follows:

- Keys **MUST** be generated and stored in secure hardware (TPM, Secure Element, or TEE) where available; hardware-stored keys **MUST NOT** be exportable.
- Where only software storage is possible, implementations **MUST** provide at-rest encryption, integrity protection, and OS/process isolation (e.g., a dedicated key service with strict ACLs).
- Where neither is feasible (e.g., MCU-class devices without secure storage), implementations **SHOULD** apply the strongest key protection available.
- Implementations **MAY** support attestation evidence of key provenance (e.g., TPM quotes, TEE reports). A future SUP is expected to define key-protection classification, attestation formats, and verification semantics.

## 7. Security considerations

The device-specific threats addressed by this profile:

| Threat | Description | Mitigation |
| :----- | :---------- | :--------- |
| **Private Key Compromise** | An attacker exfiltrates a device's private key. | Keys protected per [§6 Device Key Protection](#6-device-key-protection); MIS renewal **MUST** require fresh proof of possession before issuing a replacement SVID. |
| **Replay or Theft of SVIDs** | An intercepted device SVID is reused outside its intended context. | SVIDs **MUST** be short-lived per [§4 Profile-specific constraints](#4-profile-specific-constraints-on-the-x509-svid-profile); verifiers **MUST** validate the SVID chain and SPIFFE ID before authorization. |
| **Certificate Revocation Lag** | Revocation events are not propagated promptly. | The v0 draft relied on short SVID lifetimes for revocation-by-expiry. A standardized revocation list endpoint is sketched in [`miaf-revocation-list.md`](miaf-revocation-list.md). |
